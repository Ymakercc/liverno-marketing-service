## 系统定位与架构

这是面向外贸 B2B 获客和邮件营销运营的内部控制台，整合 CRM 客户筛选、企业和联系人补全、网站研究、AI 辅助判断与邮件草稿、发送队列、邮件事件回传、客户回复监控和运营看板。

它不是纯 n8n 工作流，也不是可自主决定并执行所有操作的 Agent。当前实现大致为：

```text
浏览器控制台（public/ 原生 HTML/CSS/JS）
          │ 同源 HTTP API
          ▼
Node.js 单体服务（src/server.mjs：API、静态文件、鉴权和服务组装）
          ├── 业务服务：客户补全、营销编排、邮箱监控
          ├── SQLite 本地队列与投递/收件状态
          ├── 孚盟、Apollo、飞书、Brevo、IMAP、AI 服务适配
          └── n8n 工作流定时调用部分自动化 API
```

AI 用于有限语义任务，例如企业匹配/筛选辅助、开发信草稿和回复意图分类。确定性业务代码负责规则、权限、状态、发送门槛、额度、幂等和调度。

## 主要业务流程

1. 从孚盟 CRM 获取候选客户和联系人，并按规则过滤。
2. 通过 Apollo 补充或匹配企业、联系人及邮箱信息。
3. 研究企业网站，由 AI 辅助生成企业判断、客户画像、产品建议和个性化草稿，代码进行邮件质量检查。
4. 在本地 SQLite 记录队列和状态，按客户时区、发送额度、去重与抑制规则排程。
5. 由 Brevo 发送邮件；Webhook 回传投递、打开、点击、退信、退订等事件，并更新本地状态/飞书汇总。
6. 第二轮邮件依据首轮发送、打开、退订/投诉/退信状态及等待工作日规则入队。
7. IMAP 监控企业邮箱；固定规则识别退订、自动回复和无关邮件，其余邮件由 MiMo 分类，必要时同步飞书并暂停后续营销。

真实运行可能调用第三方、发送邮件或写入 CRM/飞书。读取或本地预览不等于授权执行这些副作用。

## 技术栈与入口

- Node.js ESM，`package.json` 要求 Node `>=22.13`。
- 后端使用 Node 内置 HTTP 服务；依赖包括 `imapflow`、`mailparser`、`sanitize-html`、`countries-and-timezones`。
- 前端是 `public/` 下的原生 HTML/CSS/JavaScript，与后端同仓、由同一服务提供。
- `.data/` 保存本机状态，核心持久化使用 SQLite；这是本地数据目录，不应按无用文件清理。
- `npm start` 启动 `node src/server.mjs`；`npm run dev` 使用 Node watch 模式。
- `npm test` 运行 Node 测试（本文整理时未运行）。
- 当前命名的 n8n 工作流在 `workflows/kulon-*.json`；提供 `npm run n8n:validate` 与 `npm run n8n:prepare-import`。

## 重构必须保留的业务约束

- 营销、Apollo 研究、邮件发送、孚盟写回、第二轮营销和邮箱监控等开关相互独立；实际默认值需从当前代码和配置核对。
- 所有第三方调用和发送都必须经过服务端权限、资格、额度和状态校验；AI 输出不能绕开门槛。
- 队列须支持幂等、防重复发送、客户时区、每日额度、退订/投诉/硬退信抑制、状态追踪和可审计恢复。
- Webhook 和 IMAP 邮件可能重复、延迟或乱序，处理应可重试并维护一致状态。
- 密钥和邮箱授权信息不能进入前端、日志、文档、版本库或 n8n 明文载荷。`.env` 和 `.data/` 不应上传给 ChatGPT。
- SQLite 可能承担业务状态、队列、幂等和投递事件职责。迁移前需盘点 schema、事务、唯一约束、数据规模和备份恢复。
- 仓库里的 n8n 模板不能证明线上工作流的启用状态或所用版本。
